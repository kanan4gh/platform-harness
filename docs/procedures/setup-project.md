# setup-project 手順（初回プロジェクトセットアップ）

プロジェクトの6つの永続ドキュメントを対話的に作成する手順書です。ハーネス中立の正であり、各ハーネスの呼び出し口(Claude Codeでは `/setup-project` コマンド)はこの手順書に対応します。

**実行タイミング**: 検証済み配布物から新しいリポジトリを作成した直後。通常は配布専用の`platform-harness-template`を使用し、正典開発用の`platform-harness` checkoutでは実行しない。

## 作業単位(ブランチ・コミット・PR)

setup-projectは、フィーチャーブランチ上で文書を作り、PRでmainへマージする。

- **ブランチ**: ステップ0で、最新のmainから `feature/setup-project` を作成する。mainへ直接コミットしない
- **コミット**: 承認ゲートで「承認」された文書ごとに1コミットする(Conventional Commits形式。例: `docs: add product requirements (setup-project 1/6)`)。承認前の文書はコミットしない。「スキップ」した文書は変更がないためコミットしない。承認済みドキュメントの訂正は独立のコミットにする(下の「承認済みドキュメントの訂正」)
- **PR**: ステップ7で、品質ゲートの後、ユーザーに確認してからpushしPRを作成する。マージはユーザーが判断する

**IssueとステアリングについてはAGENTS.mdの規約の例外とする**: AGENTS.md は作業ごとにGitHub Issueとステアリングをセットで作り、フィーチャーブランチとPRに対応させる(Issue・ステアリング・ブランチ・PRの1対1)。setup-projectはこの規約の例外であり、ブランチとPRだけを対応させ、GitHub Issueとステアリング(`.steering/`)を作らない。理由は次のとおり。

- `.steering/` は「今回何をするか」を機能実装の単位で管理するものである。setup-projectは、機能実装(add-feature)が前提とする永続ドキュメントそのものを作る初期化であり、計画承認の代わりに文書ごとの承認ゲートを持つ
- steering 手順は、日付付きステアリングが0件の状態(配布直後・setup-project直後)を正常として扱い、完了検査をスキップする。setup-projectがステアリングを作らないことは、この前提と一致する

## ステップ0: 作業ブランチの作成とインプットの読み込み

1. 最新のmainから `feature/setup-project` ブランチを作成する。ハーネスが作業ツリー分離を提供する場合は併用してよい。作成に失敗した場合(名前の重複等)はユーザーに報告して中断し、暗黙にリネームしない
2. `docs/ideas/` 内のマークダウンファイルを全て読み、内容を理解してPRD作成の入力にする(`docs/ideas/initial-requirements.md` が推奨のファイル名)
3. **`docs/ideas/` がない、またはマークダウンファイルがない場合は、対話形式で要求を聞き取る**(配布物には `docs/ideas/` が含まれないため、配布直後はこの経路が既定になる)。聞き取る項目:
   - **プロジェクトの目的**: プロダクトを作る目的に加え、プロダクト以外の目的(例: 学習、技術検証、プロセスの検証)があればそれも聞く。PRDの成功指標に反映する
   - 解決したい課題
   - ターゲットユーザー
   - 実装したい主要機能
   - MVPの範囲
4. 聞き取った内容は `docs/ideas/initial-requirements.md` に保存し、ステップ1のPRDと同じコミットに含める(PRDの入力を会話の外に残し、後で訂正ややり直しのときに立ち返れるようにするため)

## 承認ゲート(全ドキュメント共通)

各ドキュメントの作成後、選択肢を明確に提示して承認を確認し、ユーザーの回答を得てから次に進む:

```
質問: 「[ドキュメント名]を作成しました。内容を確認してください。どうしますか?」
選択肢:
  1. 承認して次へ (推奨)
  2. 修正を指示する → 修正点を聞き、反映後に再度この質問を行う
  3. このドキュメントをスキップ → 既定テンプレートのまま残し、次のステップへ
```

ハーネスが構造化された確認UI(選択式の質問ツール等)を提供する場合はそれを優先する(利用方法はハーネスアダプタが定義)。テキストで確認する場合も、上記の選択肢を明示して回答を待機する。

**承認されたら、次のステップへ進む前に、その文書をコミットする**(作業単位を参照)。

## 承認済みドキュメントの訂正

後続のドキュメントを作成している途中で、承認済みのドキュメントに誤り(後続の文書と矛盾する記述、事実の誤り、記載漏れ等)を見つけた場合は、次の順序で訂正する。

1. 作成中のドキュメントの作業を区切る。**承認を求める前に、承認済みドキュメントを編集しない**
2. 誤りの箇所と訂正案をユーザーに示し、承認ゲートと同じ形式で回答を得る。選択肢: 訂正を承認する / 訂正内容を指示する(反映した訂正案で再度確認する) / 訂正しない
3. 承認された場合だけ編集し、作成中のドキュメントとは**独立のコミット**にする(例: `docs: fix product requirements success metrics`)
4. 作成中のドキュメントの作業に戻る

複数の誤りを同時に見つけた場合は、まとめて示してよい。コミットは訂正する文書ごとに分ける。

## ステップ1〜6: ドキュメントの作成

各ステップで対応する作成ガイド(Claude Codeではスキルとして提供)を読み込み、既存ドキュメントを踏まえて作成し、承認ゲートを実行する:

| ステップ | 作成ガイド | 生成ファイル | 備考 |
|---------|-----------|-------------|------|
| 1 | prd-writing | docs/product-requirements.md | ステップ0の入力(`docs/ideas/` または聞き取り)を元に、ユーザーストーリー・受け入れ条件・非機能要件・成功指標を具体化。成功指標にはプロジェクトの目的(プロダクト以外の目的を含む)の達成も含める。**以降すべての土台になるためスキップ選択肢は提示しない**(承認/修正のみ) |
| 2 | functional-design | docs/functional-design.md | PRDを読んでから作成 |
| 3 | architecture-design | docs/architecture.md | 既存ドキュメントを読んでから作成 |
| 4 | repository-structure | docs/repository-structure.md | 同上 |
| 5 | development-guidelines | docs/development-guidelines.md | 同上 |
| 6 | glossary-creation | docs/glossary.md | 同上 |

**空のテンプレートの扱い**: 生成ファイルが見出し・HTMLコメント・プレースホルダーだけの状態(配布直後の状態)なら、作成ガイドのいう「既存のドキュメント」とみなさず、新規作成として扱う。プロジェクト固有の記述がすでにある場合だけ、既存のドキュメントとして構造と内容を維持しながら更新する。

## ステップ7: 品質ゲートとPR

1. ローカル品質ゲート(AGENTS.md技術スタック固有層の単一ゲート。例: `uv run python3 scripts/local_quality_gate.py`)を `--steering` を付けずに実行し、全緑を確認する。日付付きステアリングが0件のため、完了検査はスキップされる(steering 手順の規定)
2. 失敗した場合は原因を直す。承認済みドキュメントを直す必要があれば、「承認済みドキュメントの訂正」に従う
3. 作成・スキップしたドキュメントの一覧を示し、pushとPR作成の可否をユーザーに確認する(GitHubへの書き込みのため)
4. 承認されたらブランチをpushし、PRを作成する。PR本文: 作成したドキュメント / スキップしたドキュメント / 訂正の履歴(なければ「なし」) / 品質ゲートの結果 / **ステアリングがなく、完了検査の対象がない旨**(steering 手順の規定)
5. 作業ツリー分離を使用した場合は後片付けする。マージはユーザーの判断に委ねる

## 完了条件

- `feature/setup-project` ブランチ上で作業し、mainに直接コミットしていない
- 6つの永続ドキュメントがそれぞれ承認またはスキップされ、承認された文書と訂正がコミットされている
- ローカル品質ゲートが全緑で、ユーザーの確認後にPRが作成されている(ユーザーがpush・PRを見送った場合は、その旨を報告する)

完了時にユーザーへ報告する: 作成したドキュメントの一覧、PRのURL、今後の使い方(ドキュメント編集は会話で依頼 / 機能追加は add-feature 手順[`docs/procedures/add-feature.md`] / レビューは review-docs 手順[`docs/procedures/review-docs.md`]。呼び出し表記は使用中ハーネスのエントリポイントに従う)。
