# 設計書

## アーキテクチャ概要

本作業は手順書の構造変更である。G3の実施を時系列で見たとき、現在の手順書は「起動前」と「終了後」が欠けている。

```
                 現在                          変更後
  ┌──────────────┐              ┌──────────────┐
  │ 実施条件      │ ゲート/commit  │ 実施条件      │ ゲート/commit/権限モード
  ├──────────────┤              ├──────────────┤
  │              │              │ 権限モードの中立化 │ ← 新設（起動前）
  │              │              ├──────────────┤
  │ 共通準備      │ clone/fixture  │ 共通準備      │ clone/fixture
  ├──────────────┤              ├──────────────┤
  │ ハーネス別確認  │ 承認境界の観察  │ ハーネス別確認  │ 承認境界の観察
  ├──────────────┤              ├──────────────┤
  │ 判定          │              │ 判定          │
  ├──────────────┤              ├──────────────┤
  │              │              │ 後片付け      │ ← 新設（終了後）
  ├──────────────┤              ├──────────────┤
  │ 誤起動時      │              │ 誤起動時      │
  └──────────────┘              └──────────────┘
```

**起動前に境界が行使される状態を作り、終了後にその状態を残さない。** 現在は中の「観察」だけがあり、前後がないため、境界が行使されない状態でも観察したことになってしまう。

## コンポーネント設計

### 1. 実施条件への追加

**責務**:
- 権限モードが既定であることを、ゲート・commit固定・clean cloneと同格の実施条件として要求する

**実装の要点**:
- 既存5項目の箇条書きへ追加する。新しい概念語を導入せず、既存の「対話型IDEまたは対話型CLIを使う」と同じ粒度で書く
- 中立化できない場合の落とし方（保留 / 対象外）は既存の「判定」節の語彙をそのまま使い、判定体系を増やさない

### 2. 「権限モードの中立化」節

**責務**:
- ハーネス別の中立化手順を1箇所に集約する
- 中立化が原理的に不可能なケース（Codexのフォルダ信頼）で、代替の決定論的ゲートを指定する

**実装の要点**:
- 配置は「実施条件」の直後、「add-feature ステップ8-Bとの接続」の前とする。時系列（起動前）に合わせるため
- ハーネス別確認の各節（Claude Code / Codex / Kiro IDE / Kiro CLI）には手順を複製しない。**中立化はハーネス横断の前提条件であり、観察手順とは層が違う**ため
- Codexの能力差は事実として書く。「Claude Codeの『allowlist外を都度確認』に対応する観察はCodexでは成立しない」ことを明記し、`--sandbox read-only` での read / write の差を代替とする
- 表形式とする。3ハーネスの対比が本節の主眼であり、箇条書きでは対応関係が読めない

### 3. 「後片付け」節

**責務**:
- 付与した信頼を受け入れ後に残さない
- 決定論的clone pathの再利用による静かな無効化を塞ぐ

**実装の要点**:
- 配置は「判定」の後、「誤起動時」の前とする。誤起動時は例外処理であり末尾に置くのが自然なため
- **決定論的パスの再利用を明示的に扱う。** 実測で残存していた8件のうち4件が決定論的名（`template-acceptance` 等）であり、蓄積そのものより再利用が害の本体である
- 「観察中に永続許可を選ばない」は後片付けではないが、後片付けを不要にする予防措置として同じ節に置く

### 4. 記録テンプレートへの追加

**責務**:
- 権限モードと信頼状態を、記録の時点で必ず埋める欄にする

**実装の要点**:
- 実施情報の表に2行追加する。既存の「設定・承認ポリシー」欄と重複するが、**あの欄は自由記述であり、権限モードが未記入でも記録は成立してしまう**。独立行にすることで空欄が可視化される
- 事前条件のチェックリストへ1項目追加する
- 監査メモの「後片付け結果」は既存項目のため、信頼エントリの扱いを含める旨を明示する形にとどめる

### 5. 契約テスト

**責務**:
- 上記4点が手順書・テンプレートから失われないよう固定する

**実装の要点**:
- 既存テストのスタイル（`section()` で節を切り出し、文字列の存在と順序を検査）を踏襲する
- 節の**存在と配置順**を検査する。時系列（起動前 → 観察 → 後片付け）が設計の要点であり、内容だけ固定しても順序が崩れれば意図が失われるため
- 3ハーネスすべてが中立化表に現れることを検査する。1つ欠けると「そのハーネスは中立化不要」と読めてしまう

## 検証設計

### 段2（実挙動検証）で観察するもの

手順書の変更であるため、**定義を実データに対して1回実行して成果物を観察する**（add-feature ステップ6の「手順・定義ファイル(Markdown)」の行）。

| 記述 | 実データでの確認 |
|---|---|
| `--permission-mode manual` で起動する | `claude --help` の選択肢に `manual` が存在する |
| 信頼エントリを削除する | `~/.codex/config.toml` に対象エントリが実在し、削除対象を特定できる |
| 決定論的パスの再利用が起きうる | 残存エントリに決定論的名が含まれる |

`~/.codex/config.toml` の実編集は**ユーザーの環境設定の変更**であるため、実施の可否を別途確認する。確認が取れない場合は、削除対象の特定までを段2の観察結果とし、未実施である旨を記録する（未観察を実施済みとして記録しない。本手順書自身の原則に従う）。

## 代替案と不採用理由

| 案 | 不採用理由 |
|---|---|
| 中立化手順を各ハーネス節の中へ分散させる | 3ハーネスの対比が読めなくなる。中立化は横断的な前提条件であり、観察手順と層が違う |
| 権限モードの検査を pytest で自動化する | G3は「実セッションでしか確認できない項目だけを扱う」節である（手順書冒頭）。起動時の権限モードは静的検査で確認できない |
| 信頼エントリ削除スクリプトを `scripts/` へ追加する | 環境固有の設定ファイルを製品リポジトリのスクリプトが編集するのは責務外。手順として記述する |
| Codexの承認境界観察を「不合格」として扱う | ハーネスの能力差であって実装の欠陥ではない。既存の「対象外: 実行面が対象能力を提供しない。代替経路を記録する」に接続するのが正しい |
