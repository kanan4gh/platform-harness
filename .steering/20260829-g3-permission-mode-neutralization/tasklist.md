### 計画と実績の差分

**計画と異なった点**:

- 段3のセルフレビューで、新設した「後片付け」節の項目2が `起動前に…確認する` という前段の指示になっており、design.md に自分で書いた「起動前に境界を作り、終了後に残さない」という時系列に反していた。起動前の確認を「権限モードの中立化」節へ移し、後片付けは削除に専念させた
- その再発防止テストを「後片付け節に `起動前` の文字列が出ない」と書いたところ、**自分で書いた根拠の一文に引っかかって落ちた**。不変条件は「起動前の指示を置かない」であって言及の禁止ではないため、テスト側を指示形へ絞った。文書構造の不変条件をテストで固定するときは、禁止するのが「語」なのか「指示」なのかを先に決める必要がある

**新たに必要になったタスク**:

- 既存テスト `test_acceptance_forbids_metered_headless_modes` の節切り出しを `実施条件 → 権限モードの中立化` へ締め直した。新節を挟んだことで、切り出し範囲が意図より広くなっていた（テストは通り続けるが、検査対象が曖昧になる）

### 学んだこと

**技術的な学び**:

- Issue の数値は実測で確かめる価値がある。Issue は「`/private/tmp` 配下の過去G3 clone が18件」としていたが、実際は**信頼エントリの総数が18件で、G3 clone は8件**だった。数え違いそのものは小さいが、実測の過程で**より重要な事実**が出た
- **害は蓄積ではなく決定論的pathの再利用にあった。** 残存8件のうち `template-acceptance` / `platform-harness-acceptance` / `platform-harness-issue46-g3` / `g3-dev-tasks2-py-v1-6-1` はランダムサフィックスを持たない。同じ受け入れを2回目に実施すると1回目の信頼が先回りする。**1回目は正常に観察できるため、再現性のある受け入れ手順ほど壊れる**という逆説的な性質を持つ
- 7件はディレクトリが既に存在しなかった。**信頼エントリはディレクトリより長生きする**

**プロセス上の改善点**:

- 手順書の変更に対する段2（実挙動検証）は、「定義を実データに対して1回実行して成果物を観察する」を文字どおりやると強い。今回は書いた後片付け手順をそのまま実行し、18→11件（`/private/tmp`配下は8→1件）とTOMLの妥当性まで確認できた。**手順書に書いた操作が実際に対象を特定でき、実行でき、壊さないことを、書いた本人が一度通す**のが段2の本義だと思われる
- ユーザー環境（`~/.codex/config.toml`）を変更する検証は、実施可否を計画段階で「別途確認する」と明記しておくと止まらずに済む。design.md に確認が取れない場合の代替（削除対象の特定までを観察結果とし未実施を記録する）まで書いておいたことで、承認待ちが判断保留にならなかった

### 次回への改善提案

- Kiro の中立化行だけ他の2つより弱い。Claude Code と Codex は具体的なフラグ・パスを指定できるが、Kiro は「`allowedTools` と実挙動の一致を確認する」であり、**中立化というより検証**である。Kiro の実機受け入れを次に行うときに、永続許可の解除手段が実際にあるかを確認して具体化したい
- 本手順書は「未観察を推測で合格にしない」を原則としているが、**未中立を検知する機構は無く、人の確認に依存している**。記録テンプレートに独立行を設けたことで空欄は可視化されるが、埋めた内容が正しいかは検証されない。決定論的に検知できる範囲がないか（例: 受け入れ記録の権限モード欄が空でないことを lint する）は検討の余地がある
