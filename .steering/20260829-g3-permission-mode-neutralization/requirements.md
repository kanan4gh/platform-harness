# 要求内容

## 概要

G3対話型受け入れの実施条件に、各ハーネスの権限モード・プロジェクト信頼を中立化する手順を追加する。あわせて後片付けの節を新設し、記録テンプレートへ権限モードと信頼状態の欄を設ける。

- **関連Issue**: https://github.com/kanan4gh/platform-harness/issues/54
- **使用ハーネス**: Claude Code
- **軽量パス**: 非適用

## パス判定（**通常パス・軽量パスのどちらでも必ず記載する**。基準の正は add-feature 手順のステップ4）

- [x] 1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない
- [x] 2. 変更対象が3ファイル以下(テスト除く)
- [ ] 3. 対象文書の更新が不要
- [x] 4. データ形式・API契約の破壊的変更がない

**判定理由**:

- 基準1: 満たす。手順書へのセクション追加とテンプレートへの項目追加であり、新しい機構も依存も導入しない。判定語彙(合格 / 不合格 / 保留 / 対象外)も既存のものを使う。
- 基準2: 満たす。変更対象は `docs/procedures/harness-acceptance.md` と `docs/procedures/templates/harness-acceptance-record.md` の2ファイル。`tests/adapters/test_harness_acceptance.py` は基準の除外対象。
- 基準3: **満たさない**。`docs/procedures/harness-acceptance.md` の**実施条件そのもの**を変更する。記録例外は「変更の実体が対象文書の外にある」ことを要件とするが、本作業は変更の実体が手順書の記述そのものであり、明確に非該当である。
- 基準4: 満たす。既存の判定語彙、記録テンプレートの表構造、add-featureステップ8-Bとの接続順序はいずれも変えない。追加のみで、既存の記録が無効になる変更を含まない。

基準3を満たさないため**通常パス（3ファイル）**とする。

## G3受け入れの要否判定

- **判定**: 不要
- **理由**: 変更対象は手順書・テンプレート・テストのみである。スキル・エージェント・コマンドの定義メタデータ、権限設定、フック定義・登録、ハーネス設定ファイルはいずれも変更しない。G3の手順を変える作業だがG3自体は不要であり、これは判定基準（アダプタ構成・権限・フックを変更したか）どおりの帰結である。

## 背景

`docs/procedures/harness-acceptance.md` は「read / write / shellを別々に依頼し、承認境界を観察する」ことをG3の中核に据えているが、**実施条件に各ハーネスの権限モード・プロジェクト信頼を中立化する手順がない**。

その結果、dev-tasks2-py への v1.6.1 展開（platform-harness #52 / dev-tasks2-py PR #27）のG3で、承認境界の観察が2回、静かに無効化された。いずれもハーネス側は正常に動作しており、**観察者が気づかなければ「合格」として記録されてしまう**性質のものだった。

- **Claude Code**: `.claude/settings.json` が「読み取り・検証系のみ自動、書き込み系は都度確認」を宣言しているにもかかわらず、auto mode がこれを上書きし、allowlist外のshellとwriteでプロンプトが出なかった。宣言された境界が一度も行使されないため、設定と実挙動の一致を確認したことにならない
- **Codex**: `--ask-for-approval` を指定していたが、`~/.codex/config.toml` のプロジェクト信頼が上位で効き、承認プロンプトが出なかった

### 着手時の実測（2026-08-29）

Issueの記述を実装・実環境に対して確認した。

- `claude --permission-mode` の選択肢に `manual` が実在する（`acceptEdits` / `auto` / `bypassPermissions` / `manual` / `dontAsk` / `plan`）。Issueの提案は実行可能である
- `~/.codex/config.toml` のプロジェクト信頼エントリは**18件**、うち**8件がG3用の使い捨てclone**であった。Issueは「`/private/tmp` 配下の過去G3 cloneが18件」としていたが、正確には総数が18件でありG3 cloneは8件である
- 8件のうち**7件はディレクトリが既に存在しない**（使い捨てcloneのため）

### 蓄積の害の機序

実測により、Issueが指摘した「受け入れを繰り返すほど承認境界が観察できなくなる」の具体的な機序が特定できた。

残存エントリのうち `template-acceptance` / `platform-harness-acceptance` / `platform-harness-issue46-g3` / `g3-dev-tasks2-py-v1-6-1` は**決定論的なパス名**である（ランダムサフィックス付きのものは再利用されない）。

> **同じ受け入れを2回目に実施すると、1回目に付与した信頼が先回りして効き、承認境界が観察できない。**

1回目は正常に観察できてしまうため、**再現性のある受け入れ手順ほど壊れる**。害は「エントリが増えること」自体ではなく、決定論的パスの再利用にある。

### 付随して確認されたこと

初回セッションでCodexは「事前承認済みのコマンド接頭辞に登録されていたため」と説明したが、`config.toml` に該当する接頭辞リストは存在せず事実ではなかった。実際の原因はプロジェクト信頼である。手順書が「未観察を推測で合格にしない」としている理由が、実例で裏付けられた形になる。

## ユースケースの軸

> 受け入れ実施者が、宣言された承認境界が実際に行使される状態を起動前に確保し、行使されなかった場合はそれを「合格」ではなく「保留・対象外」として記録できる。

## 実装対象の機能

### 1. 実施条件への権限モード中立化の追加

- 対象ハーネスの権限モードが既定（宣言された境界が行使される状態）であることを起動前に確認する
- 環境側の上書き（Claude Code の auto mode、Codex のプロジェクト信頼等）が無いことを確認し、あれば中立化してから実施する
- 中立化できない場合、その項目は「保留」または「対象外」とし、能力差と代替の決定論的ゲートを記録する

### 2. ハーネス別の中立化手順

| ハーネス | 中立化 |
|---|---|
| Claude Code | `--permission-mode manual` で起動する |
| Codex | 対象プロジェクトの `trust_level` エントリを削除する。フォルダ信頼は二値のため信頼付与が起動の前提となり、承認境界は `--sandbox read-only` での read / write の差で観察する |
| Kiro | agent定義の `allowedTools` と実挙動の一致を確認する。永続許可を選ばない |

### 3. 後片付けの節の新設

現在の手順書には後片付けの節が存在しない。次を新設する。

- 受け入れ後、対象cloneのために付与した信頼エントリを削除する
- 決定論的なclone pathを再利用する場合、前回の信頼が残っていないことを起動前に確認する
- 観察中に永続許可（「今後確認しない」系）を選ばない

### 4. 記録テンプレートへの追加

- 実施情報に「権限モード」「プロジェクト信頼状態」の欄を設ける
- 事前条件に中立化の確認項目を追加する
- 監査メモの後片付け結果に信頼エントリの削除を含める

## 受け入れ条件

### 実施条件と中立化

- [ ] 実施条件に、権限モードが既定であることの起動前確認が含まれる
- [ ] 環境側の上書きの中立化と、中立化できない場合の「保留 / 対象外」への落とし方が記載される

## 成功指標

- 次回のG3で、権限モードと信頼状態が記録テンプレートに残り、未中立のまま「合格」と記録できない状態になる
- 決定論的clone pathを再利用する受け入れで、2回目に承認境界が観察できなくなる経路が塞がれる

## スコープ外

- 各ハーネスの権限モードを検査する自動化（起動前確認は人が行う。G3は対話型実機確認そのものであり、自動化は本手順の趣旨に反する）
- `~/.codex/config.toml` の信頼エントリを削除するスクリプトの提供（環境固有の設定ファイルであり、手順として記述するにとどめる）
- Claude Code の `settings.json` の権限定義そのものの変更
