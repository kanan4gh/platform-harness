# 設計書

## アーキテクチャ概要

`steering_lint.py` の完了対象の解決(`resolve_completion_target`)に、「既定の latest で、日付付きのステアリングが0件」という状態を、エラーではなく「完了検査の対象なし」として返す分岐を加える。`main` はその場合にスキップを標準出力へ表示し、通常規則の検査(`lint(project_root, None)`)を続ける。`local_quality_gate.py` は変更しない(子プロセスの標準出力をそのまま流すため、スキップの表示はゲートの出力にも現れる)。

```
--require-complete [値]
  ├─ 値 = latest(既定)
  │    ├─ 日付付き 1件以上 → 最新を完了対象にする(従来どおり)
  │    └─ 日付付き 0件   → None を返す → main が「完了検査をスキップしました」を stdout に表示
  │                          → 通常規則だけで lint(違反なしなら終了コード0)
  └─ 値 = 名前・パス(明示)
       ├─ 見つかる     → 完了対象にする(従来どおり)
       └─ 見つからない → ValueError → 終了コード2(従来どおり)
```

## コンポーネント設計

### 1. `resolve_completion_target`(`scripts/steering_lint.py`)

**責務**:
- 完了検査の値を、完了対象のディレクトリへ解決する
- 既定の latest で日付付きのディレクトリが0件のときは `None`(対象なし)を返す

**実装の要点**:
- 戻り値を `Path | None` に変える。`None` を返すのは「latest かつ 0件」の1経路だけに限る
- 明示した値の解決(`.steering` 直下の判定、見つからないときの `ValueError`)は変えない
- 0件でも明示した対象は存在しないので、従来どおり「見つかりません」で終了コード2になる

### 2. `main`(`scripts/steering_lint.py`)

**責務**:
- 完了検査が要求され、対象が `None` に解決されたとき、スキップを標準出力に表示する

**実装の要点**:
- 表示文言: `steering lint: 完了検査をスキップしました（日付付きのステアリングが0件）`
- 表示は stdout に出す(品質ゲートの出力を読む人が気づけるように。エラーではないので stderr にしない)
- スキップの後も通常規則の検査を実行し、違反があれば従来どおり終了コード1

### 3. 手順書(`docs/procedures/steering.md`)

- 「規律の担保」の完了検査の項に、0件のときはスキップされ表示されること、その場合のPR本文の扱い(ステアリングがなく完了検査の対象がない旨を書く)を追記する(1〜3行)

## 設計判断: 代替案との比較

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **採用案** | 0件のとき完了検査をスキップし、必ず表示する | 配布直後・setup-project 直後に、何も追加しなくてもゲートが通る。修正が1か所で、すべての派生プロジェクトへ配布で届く | 「ステアリングなしのPR」が完了検査を受けずに通りうる(下記の懸念) |
| 代替案A | setup-project の手順で、ステアリングを1件作る | ゲートの挙動を変えない。setup-project も記録が残る | setup-project の手順と成果物を増やす(セットアップ用の形式的なステアリングが必要になる)。配布直後(setup-project 前)の状態は救えない。add-feature 関連の手順書を並行で改訂中の U3 と、手順書の範囲が衝突しやすい |
| 代替案B | PRテンプレート・手順書に、例外として明記するだけで、ゲートは変えない | コード変更がない | 「必須の単一ゲート」が、正常な状態で失敗し続ける。失敗が常態化すると、本物の失敗を見逃す習慣を生む。人の解釈に依存する |

**採用理由**: 必須ゲートは「正常な状態なら全緑」であるべきで、日付付きのステアリングが0件の状態は、配布直後・setup-project 直後という正常な状態である。代替案Bは失敗を常態化させ、代替案Aは配布直後を救えないうえ、セットアップに形式的な成果物を増やす。採用案は、正常な状態での失敗を、表示付きのスキップに置き換えるだけの最小の変更である。

### 懸念: 「ステアリングなしの機能実装のPR」がゲートをすり抜けやすくなる

軽減策と、その有効範囲:

1. **スキップが起きる範囲は、プロジェクトの歴史の最初の区間に限られる**: ステアリングは履歴として保持する(AGENTS.md)ため、日付付きのステアリングが1件でもできた後は、スキップは二度と起きない。0件の状態は、最初の add-feature より前だけである
2. **add-feature のPRには影響しない**: add-feature 手順ステップ8は、現在のステアリング名を `--steering` で明示してゲートを実行する。明示した対象が見つからなければ、従来どおり終了コード2で止まる
3. **スキップは必ず表示する**: 黙って通さず、ゲートの出力に「完了検査をスキップしました」が残る。PRレビューでゲートの出力を見れば気づける
4. **PR本文での申告**: 手順書に、スキップした場合はPR本文でステアリングがなく完了検査の対象がない旨を書くことを定める。レビュー時の確認点になる

残るリスク: 最初の add-feature より前に、ステアリングを作らずに機能実装のPRを出し、ゲートを `--steering` なしで実行した場合は、完了検査を受けない。これは表示とPR本文の申告(人の確認)で軽減するにとどまる。機構で防ぐには「実装コードの変更があるのに0件」を検出する必要があり、変更範囲が大きくなるため今回は扱わない(振り返りに記録する)。

### 4段検証(段3)を受けた追加の判断

- **`.steering/` 自体がない場合はエラーにする(採用)**: プロジェクトルートの指定誤り(例: `scripts/` から実行して既定のcwdが誤る)を、0件と区別できずにスキップしてしまうため。配布物・setup-project後には必ず `.steering/example/` があるので、正常な状態には影響しない。スキップの条件は「latest、かつ `.steering/` がある、かつ日付付きが0件」となる
- **clean clone・手動CIで0件になるという懸念(非該当)**: 正典の `.gitignore` は `.steering/*` を無視するが、過去のステアリングは `git add -f` で追跡されており、clean cloneにも含まれる。派生プロジェクトへの配布では、`distribution/template-manifest.json` の変換でこの無視行が削除されるため、ステアリングは通常どおり追跡される。よって「1件できた後はスキップしない」という前提は、clean cloneでも成り立つ
- **日付形式を誤ったディレクトリ名(例: `2026-11-26-foo`)**: 1件以上ある状態でも見えない既存の挙動であり、今回の範囲外(記録のみ)
- **ゲートの最終行でスキップを明示する案(見送り)**: `local_quality_gate.py` を変更しない範囲としたため。スキップ表示はゲート出力の [4/5] の直後に必ず出る。後続の改善候補として振り返りに記録する

### 補足: `--require-complete latest` を文字どおり指定した場合

値 `latest` は既定値と同一として扱われるため、文字どおり指定してもスキップの対象になる。latest は「最新の日付付きのステアリング」を意味する予約値であり、名前やパスの明示ではないため、既定と同じ挙動とする。

### AGENTS.md の整合

AGENTS.md の該当記述(「PR前のローカル品質ゲートは明示対象だけ`complete`を要求する」)は、今回の変更後も正しい(明示対象の扱いは変えない)。0件時の細部は手順書(steering.md)に置き、汎用層(各プロジェクトへ手動同期する)は変更しない方針とする。ステップ7で改めて要否を判断する。

## エラーハンドリング戦略

- 新しい例外クラスは作らない。「対象なし」は例外ではなく `None` で表す(正常な状態であり、エラーではないため)
- 終了コード: 0(違反なし・スキップを含む)/ 1(違反あり)/ 2(明示対象の解決失敗)は従来の意味を保つ

## テスト戦略

### ユニットテスト(`tests/lint/test_steering_lint.py`)
- `resolve_completion_target(…, "latest")` が、0件(`example/` だけ)のとき `None` を返す
- `.steering/` 自体がないときは、latest でも終了コード2(段3の指摘で追加)
- 0件で明示した対象は、`ValueError`(見つかりません)のまま

### CLIテスト(`tests/lint/test_steering_lint.py`)
- 0件(`example/` だけ)で `--require-complete` が終了コード0、stdout にスキップの表示
- 0件で `--require-complete 20260728-missing` が終了コード2(stderr に「見つかりません」)
- 完了検査を要求しない通常プロファイルでは、スキップの表示が出ない
- 注: 通常規則も日付付きのディレクトリだけを走査するため、0件では通常規則の検査対象も存在しない(`example/` は従来から対象外)。「スキップ後も通常規則を実行する」は、`main` が `lint(project_root, None)` を呼ぶ実装で担保し、0件で違反が出ないことをCLIテストで確認する
- 既存: 1件以上で最新が未完了なら G1 で失敗(`test_cli_normal_and_completion_profiles`)が通る

### 統合テスト(`tests/scripts/test_local_quality_gate.py`)
- 実物の `steering_lint.py` を一時プロジェクトへ置き、0件の状態で `run_gate` を実行する(steering lint 以外のコマンドは成功を返すスタブ)。ゲートが終了コード0になり、steering lint が実際に通ることを確認する

### 実挙動の観察(4段検証の段2)
- 作業ツリーの内容を一時ディレクトリへ複製し、日付付きのステアリングを削除した状態で、`uv run python3 scripts/local_quality_gate.py` を実際に実行し、全緑とスキップの表示を観察する
