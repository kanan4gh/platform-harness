## タスク管理の原則

- `active`: 作業系列が継続中。未完了を許容する
- `paused`: 意図的な中断。有効な中断記録がある場合に未完了を許容する
- `complete`: 全タスクと振り返りが完了。未完了を許容しない
- 完了・技術的スキップは実態に合わせて即時記録する
- 「今日はここまで」はスキップではなく`scripts/steering_state.py pause`で記録する
- 最終品質ゲート、コミット、G3受け入れ記録、push、PRはチェックボックスにしない

### 計画と実績の差分

**計画と異なった点**:

- 計画では除外対象をフェンスとインラインコードの2種としたが、段3のセルフレビューで未閉フェンスの扱いが問題になった。`strip_code_fences()` は閉じられていないフェンス以降を全て空行化するため、C4へそのまま適用すると以降の裸プレースホルダが検出漏れになる。インラインコードには fail-closed を明記していたのに、フェンスには同じ原則を適用していなかった
- 対処として `_strip_code_fences()` が未閉フラグも返すようにし、未閉時は除外せず生テキストを検査する。公開関数 `strip_code_fences()` の戻り値と既存3呼び出し箇所の挙動は変えていない

### 学んだこと

**技術的な学び**:

- Issueの記述を実装確認なしに前提にすると修正範囲を取り違える。Issue #55 は「`strip_code_fences()` はフェンスを除去するが、インラインコードは対象外」としていたが、実際には `check_retrospective()` が `strip_code_fences()` を一度も呼んでおらず、フェンス内の `{"key": 1}` も誤検出していた。着手前の実測で範囲が広がった
- 同じ判定ロジックが `steering_lint.py` と `steering_state.py` に重複しており、lint側だけ直してもIssueが報告した実症状（`complete` が拒否される）は消えなかった。共有関数 `find_retrospective_placeholders()` への集約が、修正の正しさと重複解消を同時に満たした
- 「検査対象から除外する」変更は、除外に失敗したときどちらへ倒れるかを毎回決める必要がある。インラインコードは同一行で閉じたときだけ除外、フェンスは閉じたときだけ除外、という fail-closed で揃えた

**プロセス上の改善点**:

- 軽量パスの段3セルフレビューが、計画時に想定していなかった検出漏れを実際に捕まえた。縮約しても段3を省かない価値が確認できた
- 段2の実挙動検証で、修正前スクリプトを `git show HEAD:` で取り出して同じ入力を通し、exit=1 → exit=0 の対比を取った。テスト通過だけでは「この変更が原因で直った」と言えないため、対比は有効だった

### 次回への改善提案

- C4以外にも生テキストへ正規表現をかけている検査がないか、横断で棚卸しする価値がある。`find_incomplete_tasks()` は「コードフェンスも安全側で検査対象にする」と明示的に生テキストを見ており意図的だが、意図が明示されていない箇所は誤検出の予備軍になる
- 本修正はリリース後、`docs/procedures/derived-project-rollout.md` に従って outfit-studio と dev-tasks2-py へ展開する。outfit-studio は `PLACEHOLDER_PATTERN` の文字クラスを絞る派生固有差分を持つため、同期時にこの正典修正で置き換えられるか（差分を温存すべきか）をG2で裁定する必要がある
