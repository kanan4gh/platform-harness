## G3受け入れの要否判定

- **不要**。
- 変更するのは、手順書(`docs/procedures/add-feature.md`、`docs/procedures/derived-project-rollout.md`)、テンプレート(`docs/procedures/templates/requirements.md`)、`.steering/example/` の見本、テスト、Claude アダプタ `.claude/commands/add-feature.md` の**本文**だけである。frontmatter(`description`)・ファイル名・配置は変えない。
- スキル・エージェント・コマンドの定義メタデータ、権限設定(`.claude/settings.json`)、フックの定義・登録、`.kiro/agents/sdd.json`、MCP 設定は、いずれも変更しない。
- **判定基準そのものを変える作業であるための注意**: 本作業は G3 基準の「ハーネス設定ファイル」の範囲を明確化する。改訂前と改訂後の両方の基準で、自身を判定した。
  - **改訂前の基準**(アダプタ構成・権限・フック・ハーネス設定ファイル): いずれにも該当しない。アダプタは本文の手順記述だけの書き換えで、これは「不要」に明記された例である。
  - **改訂後の基準**(含める: 権限・フック・承認ポリシーの設定、MCP サーバーの有効化・許可(`settings.json` 側)、定義メタデータ。含めない: `.mcp.json` のサーバー定義、品質ゲートが検証する開発ツール設定、サンプル設定): いずれにも該当しない。
  - 両方の基準で結論が一致するため、新しい基準を自分に有利に先取りした判定にはなっていない。
- 基準の文言変更は、ハーネスの表示・実読込・承認境界・Stop 挙動のいずれも変えない。変わるのは、次回以降の add-feature 実行時に、エージェントが読む判断材料である。その効果の確認は、派生プロジェクトでの R1・R2 のやり直し(上位計画 B-2)で観察される。

- neo#59 項目2: Claude アダプタの段2が `Skill('verify')` を指定している。利用できない環境では、注記に従って段2をスキップするため、実挙動の検証が抜ける
- neo#59 項目3: 派生プロジェクトの文書は、画面の受け入れ条件を「手動で確認する」とする。一方 add-feature は、承認後ステップ8まで止まらない。両者の両立方法が定められていない
- neo#60: 次の3点
  - ステップ8-A「全変更をコミットする」と、実装フェーズごとのコミットとの関係が読み取れない
  - `.steering/example/` が旧形式である(「作業状態」の節がない等)
  - G3 判定基準の「ハーネス設定ファイル」に、`pyproject.toml` の品質ゲート設定や `.mcp.json.example` が含まれるか読み取れない

## ユースケースの軸

add-feature を実行するエージェントが、検証手段の有無や画面確認の有無にかかわらず、承認後に止まらず進みながら、観察できなかった項目を黙って落とさずに PR で人へ引き渡せるようにする。

## 実装対象の機能

### 1. 段2の代替観察(neo#59 項目2)
- 段2の観察方法を、変更種別ごとに具体化する: 実行可能コード / 画面のあるアプリ / 手順・定義ファイル / 純ドキュメント
- ハーネスの検証支援機能(Claude Code の `Skill('verify')`)が使えない場合は、代替の観察方法(シェルで直接起動、ブラウザーの自動操作)へ切り替える。スキップはしない
- いずれの手段でも観察できない項目は、「未確認」として理由付きで tasklist.md に記録し、PR 本文に明記する
- 手順書(正)と Claude アダプタの両方に反映する

### 2. 受け入れ条件の確認方法の計画(neo#59 項目3)
- ステップ4で、受け入れ条件ごとに確認方法(自動テスト / エージェントの実機操作 / 人の確認)を決め、requirements.md に記録し、ステップ4.5で計画と一緒に提示する
- 承認後は止まらない。「人の確認」の項目と、実機操作で観察できなかった項目は、PR 本文の「人の確認が必要な項目」に載せる。マージ前に人が確認する

### 3. コミットの単位とタイミング(neo#60)
- 実装中の、目的単位のローカルコミットを許可する(push はステップ8まで行わない)
- ステップ8のコミット(8-A 手順3 / 8-B 候補コミット)は、未コミットの変更すべて(ステアリングの完了記録を含む)を対象とする。手順書とアダプタで同じ記述にする

### 4. `.steering/example/` の更新(neo#60)
- 見本の3ファイルを、現在のテンプレート(`docs/procedures/templates/`)の形式に合わせる
- 見本とテンプレートの形式のずれを、テストで検出する

### 5. G3 判定基準の範囲の明確化(neo#60)
- 「ハーネス設定ファイル」に含めるものと、含めないものを具体的に列挙する(手順書とアダプタ)
- `derived-project-rollout.md` フェーズ4の基準は、add-feature ステップ4を正として参照する
