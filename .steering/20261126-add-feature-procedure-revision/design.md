## 各項目の方針(選択肢と推奨)

### 項目1: 段2の代替観察(neo#59 項目2)

| 選択肢 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | 「スキップ」を「代替の観察方法」に置き換える。それでも観察できない項目は、「未確認」として理由付きで tasklist の段2行に記録し、PR 本文に載せる | 検証が黙って抜けることがなくなる。無停止の原則も保てる |
| B | スキップを維持し、スキップした旨を PR に書くことだけを追加する | 実挙動を観察する努力が要求されず、根本原因が残る |

- 手順書の段2の表は4種別にする。
  - 実行可能コード(スクリプト・CLI・フック): 実際に起動し、入出力を観察する。検証支援機能がなければ、シェルで直接起動する。
  - 画面のあるアプリ: ブラウザー等の自動操作で、操作と表示を観察する(使える場合)。
  - 手順・定義ファイル: 従来どおり。
  - 純ドキュメント: 従来どおり。
- **「観察対象がない」(純ドキュメント → スキップを記録)と、「観察手段がない」(→ 未確認として記録し、PR に明記)を書き分ける。**
- 段2の行を `[x]` にする条件: 変更種別ごとに観察を試み、観察できなかった項目を「未確認(理由)」として記録し終えた時点で `[x]` にする。
- Claude アダプタは `Skill('verify')` を名指ししない(実在しない環境があり、名指しが今回の欠陥の根本原因である)。次のように割り当てる。
  - 実挙動確認のスキル(例: `run`)が使えれば利用する。使えなければ `Bash` で直接起動する。
  - 画面は、claude-in-chrome / playwright 等のブラウザー自動操作 MCP が接続されていれば利用する。
- **トレードオフ**: ブラウザー系 MCP ツールは `settings.json` の自動許可にないため、実行中に権限プロンプトが出ることがある。これを避けるために許可を足すと、権限変更になって G3 が必要になる。本作業では足さない。プロンプトは許可境界の正常な行使であり、無停止の原則(ユーザーに判断を仰がない)とは別物として扱う。
- 注記(アダプタ L190)のうち `verify` の部分は、代替観察への切り替えに置き換える。**`code-review` が使えないときの段3スキップは据え置く**(範囲外。手順の不備として振り返りに記録し、別 Issue 候補とする)。

### 項目2: 受け入れ条件の確認方法と無停止の両立(neo#59 項目3)

| 選択肢 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | ステップ4で、受け入れ条件ごとに確認方法(自動テスト / エージェントの実機操作 / 人の確認)を決めて requirements.md に記録する。ステップ4.5では、検証方針の一部として提示する。承認後は止まらず、人の確認項目と、実機操作で観察できなかった項目を、PR 本文の「人の確認が必要な項目」へ引き渡す。マージ前(G4)に人が確認する | 承認ゲートは1つのまま。人の確認は、もともと人が判断するマージの直前に寄せる |
| B | 画面確認のために、ステップ6の後へ2つ目の停止点を設ける | 「承認ゲートはステップ4.5の1箇所のみ」の原則を壊す |

- **新たな承認ゲートは設けない**ことを明記する(パス判定と同じ扱い)。
- プロダクト固有層が「人の確認」と定めた条件の扱い: エージェントは自動で可能な観察(起動・スクリーンショット等)を行い、証跡を PR に添える。合否の判定は人に残す。
- 人の確認で不合格になった場合の戻り方: 8-B の「G3 が不合格または保留だった場合」に準じる。手順は、`resume`、影響する段から再検証、振り返りへ追記、`finish`、最終ゲート、コミット、push である。
- テンプレート `requirements.md` の受け入れ条件の各行に、`(確認方法: …)` の記入欄を設ける。PR テンプレートに「人の確認が必要な項目」の節を追加する。

### 項目3: コミットの単位とタイミング(neo#60)

| 選択肢 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | ステップ5〜6の間は、目的単位のローカルコミットを任意で許可する(Conventional Commits)。push はステップ8で行う。ステップ8のコミットは「未コミットの変更すべて(ステアリングの完了記録を含む)」を対象にする | 実装フェーズごとのコミットとの関係が明確になる。ステップ7の `finish` で tasklist は必ず変わるため、ステップ8のコミットが空になることはない |

### 項目5: G3 判定基準の範囲(neo#60)

判定の軸を明文化する: **「G3 が観察する対象(スキル・エージェントの表示と実読込、承認境界、Stop 挙動)を変える設定か」**。列挙にない設定が出てきたときは、この軸で判定する。

- **含める(G3 要)**:
  - 権限・フック・承認ポリシーを定義するハーネス設定(`.claude/settings.json`、`.kiro/agents/*.json`、Codex のプロジェクト設定(`.codex/config.toml`・`.codex/hooks.json` がある場合))
  - **MCP サーバーの有効化・許可**(`settings.json` 側の設定。プロジェクトの MCP サーバーの有効化指定、MCP ツールの許可規則)。承認境界を変えるため
  - スキル・エージェント・コマンドの定義メタデータ(frontmatter・ファイル名・配置。`.codex/agents/*.toml` を含む)
  - フックの定義・登録
- **含めない(G3 不要)**:
  - 品質ゲートが検証する開発ツール設定(`pyproject.toml` の lint・型検査・テストの設定。品質ゲートの結果で確認する)
  - **`.mcp.json` そのもの**(MCP サーバーの定義。G3 の観察対象ではない)
  - 有効でないサンプル設定(`.mcp.json.example` 等)
- **MCP の扱い(ステップ4.5で石原さんの指示により確定)**: 計画の初版では、`.mcp.json` を「含める(上位の案)/ 含めない(推奨)」の二択で示した。石原さんの指示により、次の切り分けで確定した。
  - 有効化・許可(`settings.json` 側)は、G3 の対象に含める。
  - サーバーの定義(`.mcp.json`)は、G3 の観察対象ではないため含めない。

  上位の案の「有効な MCP 設定」が指していたのは、前者(有効化・許可)にあたる。

- 参照の向きは一方向にする: add-feature ステップ4を正とし、`derived-project-rollout.md` フェーズ4は「add-feature ステップ4の基準で判定する」と参照する。add-feature 側の「rollout フェーズ4と同じ基準」という相互参照は削る。
- テストが要求する文言(「ハーネスのアダプタ構成・権限・フックを変更したか」「手順記述だけを書き換えた変更」)は維持する。
