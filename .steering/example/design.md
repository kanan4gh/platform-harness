# 設計書

> **これは記入例である**(`requirements.md` と同じ架空の作業)。該当しない節は、節を消さずに「該当なし」と書く。

## アーキテクチャ概要

既存のレイヤー構成(モデル → 保存処理 → CLI / 画面)を踏襲し、タスクのモデルに省略可能な属性 `due` を追加する。

```
Task(due: date | None) → TaskStore(JSON 保存) → CLI(add / edit / list)
                                            └→ 一覧画面(テンプレート + スタイル)
```

## コンポーネント設計

### 1. Task モデル

**責務**:
- 期限 `due` を保持し、`is_overdue(today)` で期限切れを判定する

**実装の要点**:
- `due` は省略可能とし、既存データ(`due` なし)をそのまま読めるようにする
- 判定は引数の `today` で行い、テストで日付を固定できるようにする

### 2. CLI と一覧画面

**責務**:
- `--due` の受け取りと検証、一覧での期限切れの強調

**実装の要点**:
- 日付の形式が不正なら、保存せずに終了コード 1 で終える
- 画面の強調は既存のスタイル変数を使い、色だけに頼らずアイコンも付ける

## データフロー

### 期限付きタスクの追加
```
1. ユーザーが `add "請求書を送る" --due 2026-01-31` を実行する
2. CLI が日付を検証し、Task を作る
3. TaskStore が JSON に保存する
```

## エラーハンドリング戦略

### カスタムエラークラス

該当なし(既存の入力エラーを使う)

### エラーハンドリングパターン

日付の解析に失敗したら入力エラーとして扱い、メッセージを表示して保存しない。

## テスト戦略

### ユニットテスト
- `Task.is_overdue` の境界(当日・前日・期限なし)
- 期限なしの既存データの読み込み

### 統合テスト
- CLI で期限を設定し、一覧に `!` が付くこと
