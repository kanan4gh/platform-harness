# 設計書

## アーキテクチャ概要

軽量パス基準は「**設計判断が発生しない変更を、検証コストの低い経路へ流す**」ための分岐である（`AGENTS.md`: 「設計判断が発生しないことが適用条件」）。基準1・2・4はこの意図を直接表現しているが、基準3だけが**代理指標**（docsを触るか）で書かれており、意図と食い違う。

```
意図:            設計判断が発生するか
基準1 (パターン踏襲・新規依存)  → 直接表現
基準2 (3ファイル以下)          → 規模の代理指標（意図的な近似）
基準3 (docs更新の要否)         → ★代理指標として不正確
基準4 (破壊的変更)             → 直接表現
```

基準3を「設計判断が発生するか」へ全面的に置き換えると判定が主観的になり、「設計判断は無かった」と自己申告して検証を軽くする余地が生まれる。そこで**基準3の機械的な判定しやすさは維持したまま、代理指標としての精度だけを上げる**方針をとる。

具体的には2点を加える:

1. **対象文書の明示** — 「どのファイルを触ったか」で判定できるようにする（判定の入力を確定させる）
2. **記録にとどまる更新の例外** — 「その文書が定める一覧・台帳への項目追加」という、外形で判別できる形に例外を限定する

例外を「設計判断が無い場合」ではなく「一覧・台帳への項目追加にとどまる場合」と外形で書くことが要点である。前者は主観だが、後者は差分を見れば判別できる。

## コンポーネント設計

### 1. `docs/procedures/add-feature.md` ステップ4（基準の正）

**責務**: 基準3の定義。

**実装の要点**:
- 対象を「`AGENTS.md` プロダクト固有層が列挙する永続ドキュメント」＋「`docs/procedures/` の手順書」と明示する
- 例外を「その文書が定める一覧・台帳への項目追加と、その理由の記述にとどまる更新」と外形で定義する
- 根拠（文書が「何を定めるか」自体は変わらない＝設計判断が発生しない）を1文で添える。根拠が無いと例外が拡大解釈される
- **抜け穴の封じ**: 「文書が定める方針・条件・手順そのものを変える更新は該当しない」と明記する
- 例外を適用した場合は判定結果を requirements.md に記録させる（既存の「暗黙に軽量化しない」方針の延長）

### 2. `AGENTS.md` プロダクト固有層（永続ドキュメント一覧）

**責務**: 基準3の判定対象の実体。

**実装の要点**:
- 未掲載の `external-automation-policy.md` / `harness-guide.md` / `derived-projects.md` を追記する
- 基準3が一覧を参照する以上、**一覧が実態からずれると基準が機能しない**。この依存関係を一覧の直後に1行で明示し、テストで固定する
- 推奨セット6件と、本プロダクト固有の追加3件は区別して並べる（複製先が推奨セットだけを持ち出せるようにするため）

### 3. ステップ5のエスカレーション条件

**責務**: 実装中に基準を満たさなくなった場合の昇格トリガ。

**実装の要点**:
- 「docs更新が必要と判明した」→「**対象文書が定める方針の変更が必要と判明した**（記録にとどまる更新は昇格しない）」に改める
- 中立手順（`docs/procedures/add-feature.md`）とClaudeアダプタ（`.claude/commands/add-feature.md`）の両方に同じ条件を置く

### 4. ステップ4.5（パス判定の提示）

**責務**: 判定結果をユーザーに可視化する。

**実装の要点**:
- 現行は「軽量パスを選択した場合は判定を提示する」という**片側だけの要求**になっている。これを「選択したパスにかかわらず、基準4項目の判定結果と結論を提示する」に改める
- 通常パスの場合は「どの基準を満たさなかったか」を示す。これが無いと、基準側に問題があって不要に通常パスへ落ちている状態（本Issueの発端）がユーザーから見えない
- **新たな承認ゲートは設けない**。ステップ4.5は「このワークフロー唯一の承認ゲート」であり、パス判定はそこで提示する計画の構成要素として扱う。ゲートを増やすと「計画は承認必須・実装は自動」の原則を壊す
- 中立手順とClaudeアダプタの両方に同じ要求を置く

### 5. `docs/procedures/templates/requirements.md`

**責務**: 判定チェックリスト。実際に判定を行い記録する面。

**実装の要点**:
- チェック項目3を新基準の文言に合わせ、例外に触れる
- 例外を適用した場合の記録欄を設ける（「記録にとどまる更新のため適用」等を書ける形にする）
- セクションを「適用時のみ記載」から**パスによらず常に記録する**形に変える。通常パスの場合は満たさなかった基準を記録する（ステップ4.5で提示する内容の裏付けになる）
- **`- **軽量パス**: 適用` の行形式は変えない**。steering lint の `LIGHTWEIGHT_PATTERN` が行末アンカーで判定しており、形式を崩すと C1（design.md 省略の許可）が壊れる

### 6. `docs/procedures/validate-implementation.md` 観点2

**責務**: 段4で軽量パスの適用妥当性を検証する側の基準。

**実装の要点**:
- 基準の列挙を新基準に合わせる。ここがずれると、正しく軽量パスを選んだ実装を validator が「昇格すべき乖離」として誤報する（Issue #36 で解消したのと同型の誤報になる）

### 7. `tests/procedures/test_lightweight_path_criteria.py`（新規）

**責務**: 基準の文言と各所の整合、および一覧と実態の一致の固定。

**実装の要点**:
- 既存の `tests/procedures/test_add_feature_ordering.py` と同じ「セクション切り出し＋文字列検証」スタイルに合わせる。ただしファイルは分ける（あちらはステップ順序の契約、こちらは基準の契約で関心が異なる）
- **一覧と実態の一致は構造検証で行う**: `AGENTS.md` の一覧に挙がった `.md` が `docs/` 直下に実在し、かつ `docs/` 直下の `.md` がすべて一覧に載っていることを双方向で確認する。文字列一致だけだと、docsが増えたときに静かにずれる
- 例外の抜け穴封じ（「方針そのものを変える更新は該当しない」）が消えたら落ちるアサーションを置く
- ステップ4.5のパス判定提示が**片側条件（軽量パス選択時のみ）に戻ったら落ちる**アサーションを置く

## データフロー

### 改訂後の基準3の判定

```
1. 変更対象に、AGENTS.md 列挙の永続ドキュメント または docs/procedures/ が含まれるか
   └ 含まれない → 基準3を満たす
2. 含まれる場合、その差分は「一覧・台帳への項目追加＋理由の記述」にとどまるか
   ├ とどまる   → 基準3を満たす（判定結果を requirements.md に記録）
   └ 方針・条件・手順そのものを変える → 基準3に抵触（通常パス）
```

### 適用例

| 変更 | 判定 |
|---|---|
| Issue #38（policy除外1行＋その正典への理由追記） | 例外に該当 → 軽量パス可 |
| 本ステアリング（基準そのものの改訂） | 方針の変更 → 通常パス |
| `docs/derived-projects.md` 台帳へ1行追加 | 例外に該当 → 軽量パス可 |
| `docs/architecture.md` の設計方針を変更 | 方針の変更 → 通常パス |

## エラーハンドリング戦略

手順の変更のため例外機構はない。誤りの検出経路:

| 誤り | 検出経路 |
|---|---|
| 例外を拡大解釈して方針変更を軽量パスで通す | 段4（validator 観点2）が「通常パスへ昇格すべき乖離」として指摘 |
| `AGENTS.md` の一覧が実態からずれる | 新規テストの構造検証 |
| 基準の文言が手順書・テンプレート・validator・アダプタ間でずれる | 新規テストの整合検証 |
| 例外の根拠・抜け穴封じの記述が消える | 新規テストのアサーション |

## テスト戦略

### ユニットテスト（新規 `tests/procedures/test_lightweight_path_criteria.py`）

- 基準3が対象文書（AGENTS.md 列挙の永続ドキュメント・`docs/procedures/`）を明示している
- 記録にとどまる更新の例外と、その根拠が記載されている
- 方針そのものを変える更新は例外に該当しない旨が記載されている
- 例外適用時に requirements.md へ記録する旨が記載されている
- ステップ5のエスカレーション条件が新基準と整合している（中立手順・Claudeアダプタの両方に同一アサーション）
- テンプレート `requirements.md` の判定チェックリスト項目3が新基準と一致している
- `validate-implementation.md` 観点2 の基準列挙が新基準と一致している
- **構造検証**: `AGENTS.md` の永続ドキュメント一覧と `docs/` 直下の `.md` 実体が双方向で一致する

### 実挙動検証（段2）

改訂後の基準3を実データに適用し、判定が意図どおりに変わることを観察する。具体的には、マージ済みの PR #39 の差分（`git show`）に対して改訂後の基準を適用し、基準3を満たす（＝軽量パスに乗れた）と判定できることを確認する。あわせて本ステアリング自身の差分が基準3に抵触する（通常パスが正しい）ことも確認し、例外が抜け穴になっていないことを実例で示す。

> **段3レビューを受けた設計変更**: 当初の記録例外は「一覧・台帳への項目追加にとどまる更新」という**外形1条件**だったが、`functional-design.md` の `## 機能一覧` へ1行足す(=新機能追加)が外形上完全に一致してしまうため、抜け穴になっていた。**「変更の実体が対象文書の外にある」を第1条件として追加**し、外形条件を第2条件へ降格した。あわせて対象文書に `AGENTS.md` 自身・ハーネスアダプタの規範記述・`docs/procedures/templates/` を含め、例外の対象操作に削除・値の更新を加えた。

## 実装の順序

1. `docs/procedures/add-feature.md` ステップ4の基準3を改訂する（他が参照する語彙の起点）
2. `AGENTS.md` の永続ドキュメント一覧を実態に合わせる（基準3の判定対象を確定させる）
3. ステップ4.5のパス判定提示と、ステップ5のエスカレーション条件を整合させる（中立手順）
4. `docs/procedures/templates/requirements.md` の判定セクションを合わせる
5. `docs/procedures/validate-implementation.md` 観点2 を合わせる
6. `.claude/commands/add-feature.md` のステップ4.5とエスカレーション条件を合わせる
7. テストを追加する

## セキュリティ考慮事項

- 本変更は検証コストの分岐を緩める方向であるため、**例外が検証回避の抜け穴にならないこと**が最大の関心事である。例外を外形（一覧・台帳への項目追加）で限定し、方針変更の除外を明記し、判定結果の記録を要求し、validator 観点2 で事後検出できる形にすることで、4重に封じる
- 品質ゲート（`local_quality_gate.py`）は軽量パスでも通常パスでも同一であり、本変更はゲートの強度に影響しない

## パフォーマンス考慮事項

- Issue #38 と同型の変更で、design.md の作成と段3・段4のサブエージェント起動が不要になる

## 将来の拡張性

- 基準2（3ファイル以下）も規模の代理指標であり、同種の精度問題を抱えうる。今回は基準3に限定するが、同じ「外形で判別できる例外を足す」パターンが再利用できる
- 一覧と実態の一致を固定する構造テストは、`docs/` に文書が増えたときの一覧更新漏れを継続的に捕捉する
