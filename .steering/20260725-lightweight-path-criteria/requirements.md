# 要求内容

## 概要

軽量パス基準3（`docs/` 永続ドキュメントの更新が不要）が、設計判断の伴わない「記録にとどまるdocs更新」でも通常パスへ落とす問題と、対象文書の範囲が未定義である問題を解消する。

- **関連Issue**: https://github.com/kanan4gh/platform-harness/issues/40
- **使用ハーネス**: Claude Code
- **軽量パス**: 非適用
- **G3受け入れ**: 不要（手順書・テンプレート・正典・テストと、Claudeアダプタ**本文**の1行のみの変更。アダプタ構成・権限・フックはいずれも不変）

## パス判定（**通常パス・軽量パスのどちらでも必ず記載する**。基準の正は add-feature 手順のステップ4）

- [ ] 1. 既存パターンの踏襲のみで、新しいアーキテクチャ要素・新規依存を導入しない
- [ ] 2. 変更対象が3ファイル以下(テスト除く)
- [ ] 3. 対象文書の更新が不要
- [x] 4. データ形式・API契約の破壊的変更がない

**判定理由**:

- 基準1: **満たさない**。判定基準に「記録例外」という新しい構造を導入する（プロセスの構成要素の追加）
- 基準2: **満たさない**。変更対象は6ファイル（テスト除く）: `AGENTS.md` / `docs/procedures/add-feature.md` / `docs/procedures/steering.md` / `docs/procedures/validate-implementation.md` / `docs/procedures/templates/requirements.md` / `.claude/commands/add-feature.md`
- 基準3: **満たさない**。`AGENTS.md`（SDDプロセス正典）と `docs/procedures/` の手順書が**定める方針そのもの**を変更する。記録例外の2条件のうち「変更の実体が対象文書の外にある」を満たさない（変更の実体が対象文書の記述そのものである）
- 基準4: **満たす**。既存ステアリングの再作成は不要で、`- **軽量パス**: 適用` の行形式（steering lint が依存）も維持する

**結論: 通常パス**（3項目が非適用）

## 背景

Issue #38 の対応（PR #39）は、実質 policy JSON への除外1行追加という機構の最小修正だったが、基準3に抵触して通常パスとなり、design.md の作成と4段フル検証（サブエージェント3体）がかかった。

抵触の理由は、`docs/external-automation-policy.md` 自身が「除外を追加する場合は、技術的理由と誤検出しないテストを同時に追加する」と要求していることにある。**機構側が記録を義務づけているせいで、設計判断が一切発生しない変更が必ず通常パスへ落ちる。**

### 問題1: 「記録にとどまる更新」と「方針の変更」が区別されていない

基準3は「`docs/` を更新するか」という変更の有無だけを見ており、その更新が

- その文書が**定める方針そのもの**を変えるのか（例: 除外を追加してよい条件を変える）
- その文書が定める**一覧・台帳へ項目を1件足すだけ**なのか（例: 除外リストに1件追加して理由を書く）

を区別しない。後者では設計判断が発生せず、軽量パスの適用意図（`AGENTS.md` が「設計判断が発生しないことが適用条件」と明記）を実質的に満たしている。

### 問題2: 「`docs/` 永続ドキュメント」の範囲が未定義

`AGENTS.md` プロダクト固有層が列挙する永続ドキュメントは6件だが、`docs/` 直下には他に `external-automation-policy.md` / `harness-guide.md` / `derived-projects.md` の3件が存在し、いずれも一覧に載っていない。基準3の「永続ドキュメント」が一覧を指すのか `docs/` 配下すべてを指すのかが定義されておらず、判定が読み手に依存する。`docs/procedures/` を含むかも書かれていない。

## ユースケースの軸

**機構の最小修正に、その正典への記録が義務づけられているだけの変更が、軽量パスで完了できる。一方で、文書が定める方針そのものを変える変更は引き続き通常パスへ落ちる。**

## 実装対象の機能

### 1. 基準3の対象文書の明示

- 対象を「`AGENTS.md` プロダクト固有層が列挙する永続ドキュメント」と「`docs/procedures/` の手順書」と明示する
- 判定が一覧に依存するため、`AGENTS.md` の永続ドキュメント一覧を `docs/` 直下の実態に合わせる（未掲載の3件を追記）

### 2. 記録にとどまる更新の例外

- その文書が定める一覧・台帳への**項目追加と、その理由の記述にとどまる更新**は基準3を満たす、と定義する
- 根拠を明記する: 文書が「何を定めるか」自体は変わらないため、設計判断が発生しない
- **抜け穴にしない**: 文書が定める方針・条件・手順そのものを変える更新は引き続き基準3に抵触する
- 例外を適用した場合は、その判定結果を `requirements.md` に記録させる（暗黙に軽量化しない既存方針の維持）

### 3. 関連箇所の整合

- ステップ5のエスカレーション条件「docs更新が必要と判明した」を新基準に合わせる
- `docs/procedures/templates/requirements.md` の軽量パス判定チェックリスト
- `docs/procedures/validate-implementation.md` 観点2 の基準列挙
- `.claude/commands/add-feature.md` のエスカレーション条件

### 4. パス判定の提示（選択したパスによらず）

現行のステップ4.5は「**軽量パスを選択した場合は**適用判定を計画と一緒に提示する」としており、通常パスを選んだ場合はその理由が提示されない。これでは「基準を満たしているのに惰性で通常パスを選ぶ」状態（＝不要な検証コスト）がユーザーから見えない。本Issueの発端である Issue #38 も、通常パスへ落ちた理由が計画時に提示されていれば、その場で基準の問題に気づけた。

- 選択したパスにかかわらず、**基準4項目それぞれの判定結果（満たす／満たさない＋理由）と結論**を計画と一緒に提示する
- 通常パスの場合は「**どの基準を満たさなかったか**」を示す
- 軽量パスの場合は4項目すべてを満たす根拠を示す（既存の「暗黙に軽量化しない」方針を維持）
- **新たな承認ゲートは設けない**。ステップ4.5は本ワークフロー唯一の承認ゲートであり、パス判定はそこで提示する計画の構成要素として確認を受ける
- テンプレート `requirements.md` の判定セクションを、適用時のみでなく**常に記録する**形に変える

### 5. 決定論的テスト

- 基準の文言と各所の整合を固定する
- `AGENTS.md` の永続ドキュメント一覧が `docs/` 直下の実態と一致することを**構造検証**で固定する（一覧が実態からずれると基準3の判定対象が不定になるため）

## 成功指標

- Issue #38 と同型の変更（機構の最小修正＋その正典への記録）が、改訂後の基準では軽量パスに乗ると判定できる
- 方針を変える変更（本ステアリング自身がその例）は引き続き通常パスへ落ちる
- 永続ドキュメント一覧が実態からずれた場合、テストが決定論的に検出する

## スコープ外

以下はこのフェーズでは実装しません:

- 基準1・2・4の変更（今回の問題は基準3に限られる）
- 軽量パスにおける4段検証の縮約ルールの変更（段3のセルフレビュー縮約・段4のスキップ可）
- 通常パス／軽量パス以外の第3のパスの新設
- 派生プロジェクトへの環流PR作成（`docs/derived-projects.md` 台帳の更新はロールアウト時に別PRで行う）
- ruff の作業ツリー走査問題（Issue #38 の積み残し。別Issueとして扱う）
