# 初回プロジェクトセットアップ

> **手順の正は `docs/procedures/setup-project.md`(ハーネス中立の手順書)。本コマンドはそのClaude Code最適化版であり、差分はツール割当(承認ゲート・訂正確認・push前確認のAskUserQuestion、品質ゲートとPRのBash/gh)、スキルロード、実行前の確認と完了メッセージの表示例(選択肢の「Recommended」表記を含む)のみ。手順の骨格を変更する場合は手順書→本コマンドの順で更新すること。**

このコマンドは、プロジェクトの6つの永続ドキュメントを対話的に作成します。

## 実行方法

```bash
claude
> /setup-project
```

## 実行前の確認

`docs/ideas/` ディレクトリ内のファイルを確認します。
```bash
# 確認
ls docs/ideas/

# ファイルが存在する場合
✅ docs/ideas/initial-requirements.md が見つかりました
   この内容を元にPRDを作成します

# ファイルが存在しない場合(配布直後はこちらが既定)
⚠️  docs/ideas/ にファイルがありません
   対話形式で要求を聞き取ってからPRDを作成します
```

## 作業単位(ブランチ・コミット・PR)

手順書の「作業単位」に従う。

- **ブランチ**: ステップ0で、最新のmainから `feature/setup-project` を作成する。mainへ直接コミットしない
- **コミット**: 承認ゲートで「承認」された文書ごとに1コミットする(Conventional Commits形式。例: `docs: add product requirements (setup-project 1/6)`)。承認前の文書・スキップした文書はコミットしない。承認済みドキュメントの訂正は独立のコミットにする
- **PR**: ステップ7で、品質ゲートの後、ユーザーに確認してからpushしPRを作成する。マージはユーザーが判断する

**IssueとステアリングについてはAGENTS.mdの規約の例外とする**: setup-projectはブランチとPRだけを対応させ、GitHub Issueとステアリング(`.steering/`)を作らない。`.steering/` は機能実装の単位であり、setup-projectはその前提となる永続ドキュメントを作る初期化だからである(steering 手順も、setup-project直後に日付付きステアリングが0件であることを正常として扱う)。

## 手順

### ステップ0: 作業ブランチの作成とインプットの読み込み

1. 最新のmainから `feature/setup-project` ブランチを作成し、同じ作業ツリーで切り替える。未コミットの入力(`docs/ideas/` のファイル、AGENTS.mdのカスタマイズ等)を引き継ぐため、作業ツリー分離(`EnterWorktree`)は使わない。作成に失敗した場合(名前の重複等)はユーザーに報告して中断し、暗黙にリネームしない
2. `docs/ideas/` 内のマークダウンファイルを全て読み、内容を理解してPRD作成の入力にする(`docs/ideas/initial-requirements.md` が推奨のファイル名)
3. **`docs/ideas/` がない、またはマークダウンファイルがない場合は、対話形式で要求を聞き取る**(配布直後はこの経路が既定)。聞き取る項目:
   - **プロジェクトの目的**: プロダクトを作る目的に加え、プロダクト以外の目的(例: 学習、技術検証、プロセスの検証)があればそれも聞く。PRDの成功指標に反映する
   - 解決したい課題
   - ターゲットユーザー
   - 実装したい主要機能
   - MVPの範囲
4. 聞き取った内容は `docs/ideas/initial-requirements.md` に保存し、ステップ1のPRDと同じコミットに含める。PRDが承認されるまでは未コミットのまま保持する。2で読んだ `docs/ideas/` のファイルが未コミットの場合も、同じくPRDのコミットに含める。以降、`docs/ideas/` の入力の誤りはPRDの訂正として扱う

### 承認ゲート(全ドキュメント共通)

各ドキュメントの作成後、**AskUserQuestionツール**で承認を確認する。テキストで「承認をお待ちします」と書いて待つ方式は使わない(機構が待機を担保する)。

```
質問: 「[ドキュメント名]を作成しました。内容を確認してください。どうしますか?」
選択肢:
  1. 承認して次へ (Recommended)
  2. 修正を指示する → 修正点を聞き、反映後に再度この質問を行う
  3. このドキュメントをスキップ → 既定テンプレートのまま残し、次のステップへ
```

**承認されたら、次のステップへ進む前に、その文書をコミットする**(作業単位を参照)。

**フォールバック**: AskUserQuestionが使えない環境では、従来どおりテキストで承認を求めて待機する。

### 承認済みドキュメントの訂正

後続のドキュメントを作成している途中で、承認済みのドキュメントに誤り(後続の文書と矛盾する記述、事実の誤り、記載漏れ等)を見つけた場合は、次の順序で訂正する。

1. 作成中のドキュメントの作業を区切る。**承認を求める前に、承認済みドキュメントを編集しない**
2. 誤りの箇所と訂正案を示し、**AskUserQuestionツール**で回答を得る。選択肢: 訂正を承認する / 訂正内容を指示する(反映した訂正案で再度確認する) / 訂正しない
3. 承認された場合だけ編集し、作成中のドキュメントとは**独立のコミット**にする(例: `docs: fix product requirements success metrics`)。コミットには訂正対象のファイルだけを含め、作成中(未承認)のドキュメントの差分を含めない(PRDの訂正では、訂正した `docs/ideas/` の入力ファイルも同じコミットに含めてよい)
4. 作成中のドキュメントの作業に戻る

複数の誤りを同時に見つけた場合は、まとめて示してよい。コミットは訂正する文書ごとに分ける。「訂正しない」が選ばれた誤りは、ステップ7のPR本文に「見送った訂正」として記録する。

### 空のテンプレートの扱い(ステップ1〜6共通)

生成ファイルが配布時のテンプレートから変更されていない(リポジトリを作成した時点のコミットから差分がない)なら、スキルのいう「既存のドキュメント」とみなさず、新規作成として扱う。テンプレートに含まれる見出し・HTMLコメント・プレースホルダー(`[...]` 等)・「（例）」等の例示行・サンプルのコードブロックは、プロジェクト固有の記述ではない。プロジェクト固有の記述が加えられている場合だけ、既存のドキュメントとして構造と内容を維持しながら更新する。スキップして空のテンプレートのまま残った文書は、後続のドキュメントを作成するときの入力にしない。

### ステップ1: プロダクト要求定義書の作成

1. **prd-writingスキル**をロード
2. ステップ0の入力(`docs/ideas/` または聞き取りの内容)を元に`docs/product-requirements.md`を作成
3. 壁打ちで出たアイデアを具体化：
   - 詳細なユーザーストーリー
   - 受け入れ条件
   - 非機能要件
   - 成功指標(プロジェクトの目的にプロダクト以外の目的があれば、その達成も含める)
4. 承認ゲートを実行(PRDは以降すべてのドキュメントの土台になるため、**スキップ選択肢は提示しない**。承認/修正の2択+Other)

### ステップ2: 機能設計書の作成

1. **functional-designスキル**をロード
2. `docs/product-requirements.md`を読む
3. スキルのテンプレートとガイドに従って`docs/functional-design.md`を作成
4. 承認ゲートを実行

### ステップ3: アーキテクチャ設計書の作成

1. **architecture-designスキル**をロード
2. 既存のドキュメントを読む
3. スキルのテンプレートとガイドに従って`docs/architecture.md`を作成
4. 承認ゲートを実行

### ステップ4: リポジトリ構造定義書の作成

1. **repository-structureスキル**をロード
2. 既存のドキュメントを読む
3. スキルのテンプレートに従って`docs/repository-structure.md`を作成
4. 承認ゲートを実行

### ステップ5: 開発ガイドラインの作成

1. **development-guidelinesスキル**をロード
2. 既存のドキュメントを読む
3. スキルのテンプレートに従って`docs/development-guidelines.md`を作成
4. 承認ゲートを実行

### ステップ6: 用語集の作成

1. **glossary-creationスキル**をロード
2. 既存のドキュメントを読む
3. スキルのテンプレートに従って`docs/glossary.md`を作成
4. 承認ゲートを実行

### ステップ7: 品質ゲートとPR

1. `Bash('uv run python3 scripts/local_quality_gate.py')`を `--steering` を付けずに実行し、全緑を確認する。日付付きステアリングが0件のため、完了検査はスキップされる
2. 失敗した場合は原因を直す。承認済みドキュメントを直す必要があれば、「承認済みドキュメントの訂正」に従う。直した後、1を再実行して全緑を確認する
3. 作成・スキップしたドキュメントの一覧を示し、**AskUserQuestionツール**でpushとPR作成の可否を確認する(GitHubへの書き込みのため)
4. 承認されたらブランチをpushし、`gh pr create`でPRを作成する。PR本文: 作成したドキュメント / スキップしたドキュメント / 訂正の履歴と見送った訂正(なければ「なし」) / 品質ゲートの結果 / **ステアリングがなく、完了検査の対象がない旨**
5. マージはユーザーの判断に委ねる。ユーザーがpush・PRを見送った場合は、コミット済みのブランチ名(`feature/setup-project`)を報告し、ブランチを残す

## 完了条件

- `feature/setup-project` ブランチ上で作業し、mainに直接コミットしていない
- 6つの永続ドキュメントがそれぞれ承認またはスキップされ、承認された文書と訂正がコミットされている
- ローカル品質ゲートが全緑で、ユーザーの確認後にPRが作成されている(ユーザーがpush・PRを見送った場合は、その旨を報告する)

```

- ドキュメントレビュー: /review-docs [パス] を実行してください
  例: /review-docs docs/product-requirements.md
」
```
